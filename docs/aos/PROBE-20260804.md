# A14 AOS Linux probe findings — 2026-08-04

Source archive: `a14-aos-kernel-probe-20260804T232829Z.tar.gz`

## Confirmed live architecture

The running UX3407RA system already provides the lower Linux hardware stack:

- Kernel `7.0.0-32-qcom-x1e` on Ubuntu 26.04.
- Device-tree compatibles `asus,zenbook-a14-ux3407ra` and `qcom,x1e80100`.
- ADSP and CDSP remote processors running.
- The machine-matched ADSP image is loaded from
  `qcom/x1e80100/ASUSTeK/zenbook-a14/qcadsp8380.mbn`.
- QRTR advertises QMI service 400, version 1, instance 0 on the ADSP node. This
  is the Snapdragon Sensor Core service used by the previous libssc captures.
- CAMSS, CCI, CSIPHY, CSID and VFE are active.
- The OV02C10 is bound to the in-tree `ov02c10` driver at CCI address `0x36`.
- The normal RGB path is linked as OV02C10 → CSIPHY4 → CSID0 → VFE0 RDI0.
- The HM1092 auxiliary/IR sensor is bound at address `0x24` through the separate
  CCI/CSIPHY0 path.

There is no IIO human-presence device yet. The missing layer is therefore the
SSC/QSH client and sensor frontend, not basic camera enumeration or QRTR
transport.

## Exact SSC wire contract recovered from earlier stages

The previous live captures establish:

| Layer | Value |
|---|---:|
| QMI service | 400 |
| QMI service version | 1 |
| QMI instance | 0 |
| SSC control request/response | `0x20` |
| SSC small/large indication | `0x21` / `0x22` |
| SUID request | 512 |
| SUID event | 768 |
| Camera handshake INIT | 576 |
| Camera handshake ACK | 832 |
| HPD configuration | 512 |
| Presence event | 928 |
| Standard sensor error event | 130 |

The camera handshake payload is:

```text
sensor_name = "ov02c10"
num_restarts_detected_since_last_successful_op = 0
camera_id = 2
```

The earlier userspace experiment reached the correct `camera_handshake` SUID
and received a successful QMI control response, but no handshake ACK 832. That
means QMI transport accepted the request while the QSH camera lifecycle did not
complete.

## Kernel work now justified

A proper first driver can be implemented entirely with existing kernel
subsystems:

1. `qmi_add_lookup()` for service 400/version 1/instance 0, avoiding hard-coded
   QRTR node and port numbers.
2. A connected in-kernel QMI client for control message `0x20` and report
   indications `0x21`/`0x22`.
3. Protobuf-minimal SUID discovery for `camera_handshake`,
   `human_presence_detect`, and `camera_face_detect`.
4. Camera INIT 576 and ACK 832 lifecycle handling.
5. HPD request 512 and event 928 handling.
6. IIO proximity/change-event exposure.
7. QMI-client teardown on disable and service-loss recovery.

The first development module is under `kernel/aos/`. It is intentionally not
included in the EC DKMS package and does not auto-load.

## Separate issues observed

- CDSP's `qcom_smd_qrtr` endpoint logged `-ENOMEM` during boot. SSC service 400
  is on ADSP and is still advertised, so this is tracked separately rather than
  treated as proof of an AOS transport failure.
- ADSP emitted one malformed IPC-router-packet warning. Service discovery and
  earlier SSC control transactions continued to work; this needs monitoring
  during repeated tests.
- The installed kernel header package is sufficient for out-of-tree module
  builds but does not contain the full media, DTS, remoteproc and QMI sources.
  Exact source-package provenance is now collected by probe v2.
- The live kernel includes a custom `omerf,x1e80100-cci-sync` DT node and HM1092
  CCI event-sync changes. Future patches must be rebased against the actual
  Ubuntu source plus those local camera changes, not blindly against stock
  upstream.

## Probe corrections

Probe v2 fixes two report problems:

- DT numeric cells are decoded as big-endian cells based on property type, so
  `reg = <0x36>` can no longer appear as the printable character `6`.
- It no longer calls unsupported `ss -A qrtr`; it records `qrtr-lookup`, an SSC
  service-400 filter, and `/proc/net/qrtr` when available.

It also narrows firmware enumeration and records package/source/DTB provenance.
